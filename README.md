# مِعيار | Mi'yar

مساعد معرفي ذكي لفهم المعاملات المالية المعاصرة، يعتمد على مصادر موثقة،
ويستوضح المعلومات الجوهرية، ويتحقق من كفاية الدليل قبل الإجابة.

> **تنبيه:** «مِعيار أداة معرفية مدعومة بالذكاء الاصطناعي، وليست جهة فتوى. يعرض معلومات عامة موثقة من المصادر المعتمدة.»

**النسخة الحية:** https://miyar-iota.vercel.app

---

## المشكلة

يصف كثير من الناس معاملاتهم المالية بلغتهم اليومية، مثل التقسيط والتمويل والرسوم وغرامات التأخير، دون أن يعرفوا توصيفها الفقهي. والإجابات المتاحة لهم على طرفين:

- **محركات البحث ونماذج الذكاء الاصطناعي العامة:** تجيب بثقة عن كل شيء، وتخلط بين الصور المتشابهة، وقد تنسب إلى المصادر ما لم تقله.
- **السؤال الشخصي لمختص:** ليس متاحًا دائمًا.

مِعيار يقدم طريقًا ثالثًا. يفهم وصف المستخدم، ويسأل عما ينقص من معلومات جوهرية، ثم يعرض معلومة عامة موثقة من مصدر معتمد بنصه الحرفي. ويمتنع صراحةً حين لا يكفي الدليل.

## كيف يعمل مِعيار

```
User Question
→ Safety Pre-Gate
→ Structured Extraction
→ Missing Information Detection
→ Clarification
→ BM25 Retrieval
→ Evidence Sufficiency
→ Grounded Generation
→ Citation Verification
→ Safe Response
```

| المرحلة | ما تفعله |
|---|---|
| **Safety Pre-Gate** | فحص حتمي قبل أي معالجة: طلب الحكم على حالة شخصية أو نزاع يُحال، والأسئلة خارج النطاق أو بغير العربية تُوقف |
| **Structured Extraction** | النموذج يحوّل الوصف إلى بنية محددة (Zod schema). كل واقعة «صريحة» يجب أن تقتبس كلام المستخدم حرفيًا، وإلا عوملت كمجهولة |
| **Missing Information Detection** | قواعد حتمية تحدد المعلومات الجوهرية الناقصة، دون نموذج لغوي |
| **Clarification** | سؤال رئيسي واحد في كل مرة، مع خيار «لا أعرف» وحد أقصى لعدد الجولات |
| **BM25 Retrieval** | استرجاع المرشحين من قاعدة المعرفة المعتمدة فقط |
| **Evidence Sufficiency** | بوابة حتمية منفصلة عن الاسترجاع: هل تتحقق شروط انطباق السجل على المعاملة، ولا ينطبق أي استثناء؟ |
| **Grounded Generation** | النموذج يختار مراجع claims مسجلة فقط، ولا يكتب نص الحكم ولا الاقتباس بنفسه |
| **Citation Verification** | فحوص حتمية: المصدر موجود ومعتمد وموثق، ويدعم الـclaim حرفيًا، وفي حدود نطاقه |
| **Safe Response** | أي فشل في أي مرحلة يمنع عرض إجابة موثقة |

## حالات الاستجابة الست

| الحالة | المعنى |
|---|---|
| `GROUNDED` | وُجدت معلومة عامة موثقة في سجل معتمد تتحقق شروط انطباقه، وتُعرض مع نص المصدر. قد تكون مشروطة بشرط لم يُحسم، أو بنيوية تصف صورة المعاملة دون حكم عليها |
| `DISPUTED` | في المصادر المعتمدة معالجات مختلفة للمسألة، فتُعرض جنبًا إلى جنب مع مصادرها دون ترجيح. قاعدة الإنتاج الحالية لا تتضمن مواقف متعددة، فهذه الحالة غير متاحة منها، واختُبرت على test fixtures فقط |
| `NEEDS_CLARIFICATION` | تنقص معلومة جوهرية يتوقف عليها الجواب، فيسأل مِعيار عنها |
| `REFERRAL` | السؤال يطلب حكمًا على حالة شخصية أو فصلًا في حقوق أو نزاع، فيُحال إلى مختص أو جهة إفتاء |
| `INSUFFICIENT_EVIDENCE` | لا يوجد في المصادر المعتمدة ما يكفي للإجابة، فيمتنع مِعيار صراحةً |
| `TECHNICAL_ERROR` | خطأ تقني، كتعذر الوصول إلى النموذج أو انتهاء المهلة أو فشل التحقق من مخرجاته. لا تُعرض أي إجابة جزئية |

## أهم عناصر السلامة

- **لا فتوى شخصية.** الأسئلة عن حالة المستخدم نفسه أو عن نزاع تُحال، ولا يُجاب عنها بحكم.
- **لا ترجيح آلي.** يُمنع النظام من عبارات الترجيح والتفضيل، وتُعرض المواقف المختلفة كما هي.
- **لا جواب بلا دليل كافٍ.** لا تُعرض حالة GROUNDED إلا إذا ثبتت شروط انطباق السجل بوقائع صرّح بها المستخدم. القيم التي يستنتجها النموذج لا تُعد وقائع.
- **فصل الاسترجاع عن كفاية الدليل.** التشابه النصي وحده ليس دليلًا. بوابة الدليل وحدة مستقلة وحتمية.
- **التحقق من الاستشهادات.** نص كل claim واقتباسه وبيانات مصدره تأتي من السجل المعتمد لا من النموذج، وفشل claim واحد يُسقط الإجابة كلها.
- **مقاومة prompt injection:**
  - كلام المستخدم والوثائق المسترجعة بيانات لا تعليمات.
  - النص الحر الذي يكتبه النموذج يُفحص من ألفاظ الحكم والاقتباس والترجيح.
  - بيانات الاختبار الاصطناعية لا يُستشهد بها أبدًا.
- **fail-closed عند الخطأ:**
  - **قاعدة المعرفة:** أي سجل غير صالح أو غير معتمد يرفض تحميلها كلها.
  - **مخرجات النموذج:** أي مخرج مخالف للـschema أو خطأ عند المزوّد ينتهي إلى `TECHNICAL_ERROR`.
  - **حالة الاستيضاح:** أي عبث بها، وهي موقّعة بـHMAC، يُرفض.
- **الخصوصية:** لا تُخزن أسئلة المستخدمين في قاعدة بيانات. وحالة الاستيضاح تُحمل في رمز موقّع لا يتضمن نص المستخدم الخام.

## المصادر

تعتمد النسخة الإنتاجية الحالية على قاعدة معرفة مغلقة (`knowledge_base_v2.json`). تتكون من **6 سجلات** موثقة نصيًا من الموسوعة الفقهية في موقع الدرر السنية:

- الثمن المؤجل الأعلى من الثمن النقدي
- البيع بالتقسيط
- حلول الأقساط عند التأخر
- المرابحة للآمر بالشراء: وصف بنيوي فقط
- الزيادة المشروطة للمقرض
- القرض ذو الفائدة المرتبطة بالمبلغ والزمن

معنى التوثيق هنا:

- **تحقق نصي (textual verification) فقط:** كل claim مدعوم بنص حرفي من المصدر (`textual_source_match`)، والاقتباس المعروض هو المقتطف الموثق نفسه.
- **لا scholarly review:** لم تخضع السجلات لمراجعة علمية من مختص.
- **ضوابط مِعيار التحريرية:** شروط الانطباق وما لا يُعمم إليه السجل تُحفظ منفصلة عن نص المصدر.

لا يستخدم مِعيار البحث المفتوح في الإنترنت، ولا معرفة النموذج الذاتية مصدرًا شرعيًا.

## القيود الحالية

- **نطاق معرفي محدود عمدًا:** ستة موضوعات في البيع بالتقسيط والمرابحة والقروض.
- **النسخة الحالية ليست جهة فتوى**، ولا تُغني عن سؤال أهل العلم في الحالات الشخصية.
- **بعض المعاملات الحديثة قد تنتهي إلى `INSUFFICIENT_EVIDENCE`**، مثل بطاقات الائتمان والأسهم والعملات المشفرة وخدمات «اشترِ الآن وادفع لاحقًا». ليس السبب خللًا في الفهم، بل غياب مصدر معتمد يغطيها في قاعدة الإنتاج.

---

## لماذا لا نجيب دائمًا؟

الامتناع المقصود جزء من السلامة العلمية، لا عيب في المنتج.

- إجابة واثقة بلا مصدر يدعمها أخطر من عدم الإجابة.
- إجابة مبنية على مصدر لا ينطبق على صورة المعاملة تضلل السائل وإن بدت موثقة.
- تخمين معلومة جوهرية لم يذكرها المستخدم قد يغيّر الحكم كله.

لذلك:

- **حين تنقص معلومة جوهرية:** يسأل مِعيار عنها.
- **حين لا يعرفها المستخدم، أو لا يغطي المسألة مصدر معتمد:** يقول ذلك صراحةً.
- **حين يطلب المستخدم حكمًا على حالته الشخصية:** يحيله إلى مختص.

الهدف ألا يُعرض إلا ما يستطيع مِعيار توثيقه.

## Ablation Evaluation

قارنّا بوابة القرار في مِعيار الكاملة (`FULL_MIYAR`) بخط أساس يجيب من أعلى نتيجة استرجاع BM25 مباشرةً (`BM25_ONLY`). شمل التقييم 25 صفًا (19 حالة، بعضها متعدد الجولات)، وهو تقييم حتمي بلا نموذج لغوي ولا حكم آلي.

| المقياس | BM25 فقط | مِعيار كاملًا |
|---|---|---|
| مطابقة القرار النهائي (الإجابة أو عدمها، مع المصدر المطلوب) | 28% (7/25) | **100% (25/25)** |
| معدل الإجابة غير المدعومة (من كل الصفوف) | 68% (17/25) | **0% (0/25)** |
| الامتناع أو الاستيضاح الصحيح (في الصفوف التي لا تسمح بـGROUNDED) | 11% (2/18) | **100% (18/18)** |

> **تنبيه:**
> - هذه نتائج على **benchmark داخلي صغير**، وليست ادعاءً بدقة عامة.
> - صُمم الـbenchmark ضمن المشروع نفسه، ويغطي نطاق قاعدة المعرفة الحالية فقط.
> - كود التقييم ونتائجه في `eval/ablation/`: التقرير `results.md` والنتائج الخام `results.json`.
>
> لإعادة التشغيل (يعيد كتابة الملفين):
>
> ```bash
> npx vitest run --config eval/ablation/vitest.config.mts
> ```

## التشغيل محليًا

```bash
npm install
```

أنشئ ملف `.env.local` اعتمادًا على `.env.example`، وعرّف فيه المتغيرات الأربعة. لا تضع قيمًا حقيقية في Git أبدًا.

| المتغير | الوصف |
|---|---|
| `MIYAR_LLM_PROVIDER` | مزوّد النموذج. القيمة المدعومة حاليًا `openai` |
| `MIYAR_LLM_MODEL` | اسم النموذج |
| `MIYAR_LLM_API_KEY` | مفتاح الـAPI. يبقى على الخادم فقط |
| `MIYAR_STATE_SECRET` | سر توقيع حالة الاستيضاح (HMAC-SHA256)، لا يقل عن 32 حرفًا عشوائيًا |

```bash
npm run dev
```

أوامر أخرى:

```bash
npm test
npm run test:integration
npm run typecheck
npm run build
```

`npm run test:real` يستدعي النموذج الحقيقي، فيحتاج مفتاحًا صالحًا وقد تترتب عليه تكلفة.

## بنية المستودع

```
src/
  app/          واجهة Next.js العربية (RTL) ومسار الـAPI ‏/api/miyar
  pipeline/     مراحل المعالجة: pre-gate، extraction، missing info، clarification،
                retrieval، evidence، generation، citation verification، orchestrator
  domain/       الـschemas (Zod) وحالات الاستجابة والرسائل الثابتة
  kb/           تحميل قاعدة المعرفة والتحقق منها (fail-closed)
  ai/           مزوّد النموذج وschema المخرجات الصارم
  text/         أدوات تطبيع النص العربي
  config/       معجم الاسترجاع
  server/       رمز حالة الاستيضاح الموقّع
eval/fixtures/  بيانات اختبار اصطناعية، لا تُحمَّل في الإنتاج أبدًا
knowledge_base_v2.json   قاعدة المعرفة الإنتاجية
knowledge_base_v1.json   النسخة الأولى (مرجع فقط، لا تُستخدم وقت التشغيل)
test_set_v1.json, test_set_v2.json   حالات الاختبار والـbenchmark
PRODUCT_SPEC.md          مواصفات المنتج
CLAUDE.md                تعليمات التطوير
```

## خطة التطوير بعد المسابقة

- **توسيع قاعدة المعرفة:** بمصادر رسمية، مع الحفاظ على قاعدة الاقتباس الحرفي.
- **دمج توسعة قاعدة المعرفة (KB v3) تدريجيًا:** وهي غير مدمجة في النسخة الحالية. تُدمج عائلةً عائلة، ولكل عائلة اختباراتها وتشغيلها الحقيقي قبل النشر.
- **رصد الفجوات المعرفية:** تتبع الأسئلة التي تنتهي إلى `INSUFFICIENT_EVIDENCE` لتوجيه إضافة المصادر.
- **إضافة مصادر ومراجعات علمية:** مراجعة السجلات من مختصين، إضافة إلى التحقق النصي.
- **تحسين التغطية:** لبطاقات الائتمان والأسهم والعملات المشفرة وBNPL وغيرها.
